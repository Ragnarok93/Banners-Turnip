# A650 Source Audit — Build Profiles, Kernel Scope, and Vulkan Conformance

Date: 2026-10-15
Branch: `feature/a650-unified-vulkan14-20261015`

## Findings verified against the current branch

### 1. The build targets KGSL, not MSM DRM

The performance build configures Mesa with:

```text
-Dfreedreno-kmds=kgsl
```

Therefore, Linux `drm/msm` fixes to `MSM_PARAM_GMEM_BASE` and DRM-side speed-bin handling are **not direct fixes for this build configuration**. The A650 GMEM_BASE regression is real in the DRM/MSM backend, and its fix was included in Linux 7.0.11, but it must not be presented as a Turnip/KGSL patch or assumed to fix Samsung KGSL behavior. Confirm the actual target backend before investing in kernel-side work.

References:
- A650 GMEM_BASE regression and fix: https://lists.openwall.net/linux-kernel/2026/03/16/1325
- Linux stable changelog confirms the fix: https://www.opennet.me/kernel/7.0.11.html

### 2. Performance workflow was not exposing the candidate profiles

The build script already supported experimental profile logic, but the workflow only exposed `generic` and `sd865-cortex-a77`. The workflow has now been updated to expose:

- `sd865-program-reference`: borrowed graphics program state only.
- `sd865-pipeline-512k`: 512 KiB A650 pipeline suballocation only.
- `sd865-sysmem-screen`: forced SYSMEM only, as a diagnostic control.
- `sd865-combined-512k`: borrowed program state plus 512 KiB suballocation.
- `sd865-combined-sysmem`: combined candidate plus forced SYSMEM.

This separates individual diagnostic controls from combined candidates, so results can be interpreted rather than conflating unrelated changes.

### 3. Release metadata was overstating Vulkan support

The workflow repack step previously replaced every profile's `meta.json` with `driverVersion: Vulkan 1.4.335` and `minApi: 28`, overriding the build script's profile-specific metadata. That is not valid evidence of runtime API support and can misrepresent the build.

The workflow now preserves the `meta.json` generated by the build and changes only its name and description. The generic build's default metadata was also reduced from the unsupported `1.4.335` claim to a conservative `1.3.0`; this is metadata hygiene, not proof of Vulkan 1.3 conformance. The release ZIP also includes `build-manifest.json`, carrying the Mesa SHA, builder SHA, profile, patch hashes, render-mode selection, allocation size, Android API, NDK, and driver SHA-256. Release notes now identify which candidate was built.

### 4. Borrowed graphics program state remains a correctness-sensitive candidate

The patch changes command-buffer graphics program state from an owned struct copy to a pointer into pipeline-owned state. This may reduce copies, but it is not safe to accept based on compilation alone. Audit all paths that retain, clone, reset, execute, or submit command buffers; pipeline destruction; secondary command buffers; and any deferred draw-state generation. Run Vulkan validation and stress tests before benchmarking it. Keep this profile opt-in until those checks pass.

Vulkan command-buffer lifecycle and object lifetime references:
- https://docs.vulkan.org/spec/latest/chapters/cmdbuffers.html
- https://docs.vulkan.org/spec/latest/chapters/fundamentals.html
- https://docs.vulkan.org/spec/latest/chapters/pipelines.html

A focused diff review found the patch changes `tu_cmd_state.program` to a non-owning pointer, initializes it to a static zero state on command-buffer begin, and updates several draw/constant-emission call sites to dereference it. Vulkan lifetime rules mean destroying a pipeline invalidates executable command buffers that reference it, and submitted uses must finish before destruction; this is not by itself proof of a dangling-pointer bug. The unresolved part is driver-internal access outside normal valid command-buffer use: audit reset/re-record, secondary command buffers, submit-time command-buffer insertion, deferred draw-state generation, and pipeline teardown before accepting the optimization. If any valid path retains a dereference beyond pipeline lifetime, the safe alternatives are retaining a pipeline reference for the command buffer or copying the required immutable state.

### 5. Pipeline suballocation and forced SYSMEM are hypotheses

The 512 KiB allocation changes allocation granularity, not GPU instruction efficiency by itself. Measure CPU allocation cost, allocation count, memory use, fragmentation, and frame-time distribution. Forced SYSMEM bypasses normal render-mode selection and is a control for diagnosis, not a presumed performance improvement.

### 6. Vulkan 1.4 remains unproven

The API-version probe changes reported API version without implementing or validating the complete set of Vulkan 1.4 requirements. Keep it diagnostic-only. Do not stamp Vulkan 1.4 into metadata as a proxy for CTS conformance. First collect actual device enumeration and run relevant CTS suites against a pinned Mesa commit.

## Reproducible candidate matrix

Added `.github/workflows/a650-reproducible-matrix.yml`. It resolves Mesa `main` to one full commit SHA once, or accepts a caller-supplied SHA, then builds the generic baseline, Cortex-A77 baseline, each isolated A650 candidate, and the combined candidates against that exact revision. It caps parallel builds at two, does not publish releases or mutate repository contents, and uploads each build log plus any ZIP/manifest artifacts. The workflow is triggered by relevant pushes to this branch and can also be run manually. The matrix and API-probe workflows have been triggered by these commits. No candidate build result is considered validated until the jobs finish. The previous API-probe run did compile and package the probe, but its source audit failed because it scanned only `tu_device.cc` and could not see viewport-limit assignments elsewhere in the Vulkan source tree. The audit now scans the full Vulkan source directory and recognizes indexed limit assignments; rerun results are pending.

## Follow-up build-harness audit

The workflow's Ubuntu dependency install now explicitly installs `ccache`, matching `build_turnip_perf.sh`. The script uses a `pip`/`pip3` fallback when installing Mako.

The manifest currently records hashes for all three candidate patch files even when a profile did not apply them; the corresponding `*PatchApplied` booleans disambiguate this, but the fields are better understood as source patch hashes rather than a list of applied patches. A future manifest refinement should emit an explicit applied-patch list to avoid ambiguity.
